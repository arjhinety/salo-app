## Scoring definitions (PROPOSED in M1; to be confirmed by Arjhine before tuning freezes the weights)

The guide gives the four parts of a pantry's value only as an example (p.11). The engine needs exact
formulas. Each raw score is in [0, 1], and the value is the weighted sum (`src/engine/utility.ts`).

| Part | Raw score | Why |
|---|---|---|
| Need | remaining need ÷ tonight's need | A pantry that has already been promised food scores lower, which spreads food around |
| Storage | 1, or 0.2 if the lot needs a fridge if kept and the pantry has none | It can still serve tonight, so not 0 (the guide's Socorro example) |
| Distance | 1 − road km ÷ the longest donor-to-pantry road in the dataset | Closer scores higher |
| Freshness | 1 − minutes to the earliest arrival ÷ 60 | Food that arrives sooner is fresher |

Refusals (the reflex step, guide p.11), checked in this order:
1. Closed tonight, or the earliest possible arrival is after closing time (this also covers "no driver could reach it").
2. The lot is bigger than the pantry's dry storage plus fridge capacity.
3. No remaining need.

**Review flag:** the 0.2 no-fridge storage score is the main reason some pantries get nothing (see "Fairness measure check"). Review the storage formula before tuning.

Untuned starting weights for development: need 0.4, storage 0.3, distance 0.15, freshness 0.15. The share-bid scale starts at 17. Tuning on E01–E10 replaces them.

## Fairness measure check (decided 2026-10-13)

- On the tuning evenings with untuned parameters, worst-served need met was 0 on all 10 evenings for all four policies: at least one pantry with need got nothing. Pantries left with 0 kg per evening: Salo 1–3, central greedy 1–4, first-come-first-served 4–9, nearest 3–11 (`docs/reports/m1-tuning-snapshot.md`).
- **Correction (2026-10-13, prompted by a side-agent note):** this was first described as mostly structural (small, indivisible lots and scarce food). A check on the same tuning evenings shows the proposed **storage score** is the main cause. With the 0.2 no-fridge storage score, Salo leaves 1, 3, 1, 2, 2, 1, 1, 2, 1, 1 pantries with nothing, and 15 of those 16 have no fridge (16 of the 30 pantries have no fridge). With the storage part removed (weights 0.57 / 0 / 0.215 / 0.215), it leaves 0, 0, 0, 0, 1, 0, 0, 2, 0, 0, and food rescued rises from 150.2 to 155.3 kg per evening. The storage formula and weight are therefore on Arjhine's pre-tuning review list. The trade-off: the storage part is what sends cooked food to pantries that can keep it, which is the guide's Bukal-vs-Socorro example.
- **Decision (option A):** keep the guide's measure and check it again right after tuning, on the tuning evenings only. If it is still 0 on most tuning evenings, Arjhine picks a replacement measure (for example, pantries left with nothing, or the mean of the five worst-served) **before any pilot run**. No pilot or main evening may run until this check is done and recorded here.

## Hidden true show rate (APPROVED 2026-10-13, option T1: pre-tuning engine definition)

- **Problem:** the engine drew each driver's real behaviour from `frozenReliability`, the same number the agents learn. That makes the agents' estimate exactly right by construction (a circular evaluation), so learning looks better than it is.
- **Proposal (T1):** give each driver a hidden `trueShowRate` that only the simulated world reads, never the agents, the messages or the UI. Its value is the dataset generator's own `p_show`, recovered by re-running the pinned v1.2 build with read-only instrumentation; the run checks that all CSVs are byte-identical to the bundled ones. R. Dizon's history was hand-set, so his rate is one fixed seeded posterior draw, Beta(11, 2) → 0.817. The late share (12% of shows) and the 50/50 split between withdrawing and not showing match the generator. Learned estimates differ from these rates by 0.09 on average and 0.30 at most.
- **Effect on D-Q1** (Salo, tuning evenings E01–E10, untuned): with truth equal to the estimate, the "most reliable" rule cut driver failures by 60% (9.1 to 3.6 per evening). With T1 the cut is 20% (6.4 to 5.1), it rescues about 5 kg less per evening, and it strands slightly more lots. So the circular setup overstated the benefit of learning.
- **Alternative (T2):** one seeded Beta(shows + 1, misses + 1) draw per driver. It is self-contained but noisier, and it does not match how the tuning history was generated.
- No pilot or main evening is run for this.
- **Implemented:** `scripts/recover-true-show-rates.py` writes `src/engine/hiddenTruth.generated.ts`, after checking that the instrumented build reproduces all 10 bundled CSVs byte for byte. R. Dizon = 0.816575: numpy default_rng(20260927), one draw per driver in drivers.csv order, the procedure from the approved experiment. A first attempt used Python's `random` and gave 0.901; it was replaced to match the approved value. The engine reads the truth only through `RunOptions.trueShowRate` (default: the generated file). Tests check that outcomes follow the truth and that agents' PROPOSE messages carry the learned estimate.

## Driver reply delay (decided 2026-10-13, option B: pre-tuning engine definition)

- **Problem:** simulated drivers answered in the same minute the pantry won, so a lot was never visibly TENTATIVE ("held until a driver commits") in a simulated evening. Instant replies are also unrealistic.
- **Decision:** after a TENTATIVE_ACCEPT, the first driver round happens 1–3 minutes later (uniform whole minutes, a counter-based seeded draw per lot on its own RNG stream, identical under all four policies). **Extended 2026-10-13 (Arjhine, option A):** every re-announcement after a driver FAILURE (withdrawal, no-show or operator cancel) also waits 1–3 minutes. The draw is keyed by evening seed, lot and round number (0 = first round after TENTATIVE_ACCEPT, n = the lot's n-th re-announcement), on the same stream, so it is the same under all four policies; `replyDelayMaxMin: 0` still reproduces the pre-delay engine. Reason: with same-minute re-announcements a paused live Cancel driver showed FINAL again at once (594 of 665 paused cancels on E05), so the button looked broken. The delay range is an assumption; there is no measured data on real volunteers' reply times.
- **Evidence** (mobile-data study, tuning evenings E01–E10, untuned, throwaway engine copy proven identical at delay 0 on all 40 evening/policy pairs; `docs/handoffs/2026-10-13-mobile-data.md`): for Salo, max delay 3 changes food rescued by −0.07 kg per evening (150.25 → 150.18), stranded awards go from 0.3 to 0.8 per evening, and TENTATIVE lasts 1.9 minutes on average. Max delay 5 would cost 2.2 kg per evening (95% interval [−5.41, −0.05]).
- **Evidence for the extension** (mobile-data, tuning E01–E10, untuned, T1; `docs/handoffs/2026-10-13-mobile-data-reannounce-delay.md`; orchestrator re-checked the per-evening sums and regenerated the M1 snapshot): Salo food rescued 150.18 → 148.96 kg per evening, stranded awards 0.80 → 1.00, TENTATIVE lasts 2.15 minutes on average (max 6 when rounds chain). fcfs 132.66 → 133.34, nearest 143.36 → 143.38, central greedy 150.80 → 151.70 kg. Paused-cancel probe on E05: 0 of 641 cancels show FINAL again in the same minute (was 594 of 665).

## Small live-demo defaults (2026-10-13, orchestrator; change on request)

- **Live posts are not checked against the donor's closing time.** The dataset generator posts lots up to 15 minutes after a donor's listed closing time (for example, D01 closes at 17:30 but posts L0211 at 17:37), so a closing-time check would reject lots the dataset itself contains. The other live checks stay: the donor exists, pickup-by is later than the clock, and there is at least one item.
- **The play/pause simulation control stays in demo builds.** It is labelled as simulation and drives only the simulated clock.
- **A baseline replay on the dashboard is an illustration, not a result** (Arjhine, 2026-10-13). Whenever a baseline replay runs, the dashboard shows this note, kept in `src/i18n/strings.ts`: "One simulated tuning evening (E05), untuned settings — an illustration, not a result; results come only from the main evenings (Results screen)". The dashboard never prints kg totals or any Salo-vs-baseline comparison. One evening's difference has no interval and comes from a tuning evening with untuned settings, so a comparison drawn from it could pass for evidence. Comparisons appear only on the Results screen, as paired intervals on the difference over the main evenings, with no main numbers until the pilot count is recorded (RES-03, RES-06). This follows Bestgen (2022, arXiv 2205.11134), who argues for reporting bootstrap confidence intervals on the difference between systems instead of only which one scored higher (cited as on guide p.20).

## Parser development data: tuning evenings only (Arjhine, 2026-10-20, hard rule for M4)

- **Rule:** the rule-based fallback's vocabulary, synonyms, unit and number words, time phrases, and any example messages in the server prompt may be built only from `donor_messages.csv` rows of tuning evenings E01–E10. Every agent brief carries this rule. Agents filter by `evening_id` first and assert it, and never open or print pilot (E11–E20) or main (E21–E30) rows.
- **Filter used:** `donor_messages.csv` has no evening column, so each `lot_id` is joined to `food_offers.csv` `evening_id`, keeping E01–E10 only. Result: 170 rows, the same message ids as `split == "tuning"` (0 mismatches); agents re-check this by asserting both on load. The kept rows are committed as `data/parse-dev/donor_messages_tuning.csv` (sha256 `4f269299…`), with `evening_id` added; agents get only that file. The full `donor_messages.csv` is not given to them. **Exclusion (Arjhine, 2026-10-20):** the parser must not use the post form's food catalog. `src/donor/catalog.ts` builds `CATALOG` with `buildCatalog(EVENINGS)`, which reads the lots of all 30 evenings, pilot and main included. So nothing under `src/parse/` may import `src/donor/catalog` or `src/data`, and a test fails if it does. The same applies to the laptop proxy: its prompt's item list may not come from `food_offers.csv`. The parser's canonical items are the distinct gold (food item, unit) pairs of the 170 tuning messages: 21 foods. Pechay and canned sardines never appear there, so the parser flags them as unmatched and the donor picks them by hand. Mapping a parsed item to the post form's catalog (kg, load units) happens outside `src/parse/`, after parsing.
- **Scoring boundary (Arjhine, 2026-10-20):** every parser score, including any future pilot or main score, is computed on the raw `src/parse` output (`ParseResponse`), never after the donor screen maps items to `src/donor/catalog.ts`. The evaluation code (`scripts/eval-parser-tuning.ts` or the gated jest eval) imports nothing from `src/donor` or `src/data`, and the import-guard test checks it alongside `src/parse/`.
- **In-sample (Arjhine, 2026-10-20):** the fallback's vocabulary, synonyms and time phrases are built from the same 170 tuning messages it is scored on, so that score is in-sample and must never be quoted as expected accuracy.
- **Claude-path scores come from stored responses (Arjhine, 2026-10-20):** every `/parse` response in an evaluation, including errors, is saved to a JSONL file under `docs/reports/`. Each line records `message_id`, the model id, a timestamp and the run number. Scores are computed only from those saved files, never from live calls. The tuning set gets 3 repeat passes (510 calls; the recorder's dry run estimates $0.049 for all three before thinking tokens, worst case $0.56 with every call at 2,048 output tokens; real spend is taken from the logged usage), and every Claude-path score is reported with its spread across the passes next to it. No Claude-path call is made without Arjhine's go-ahead on the spend, including on the tuning set.
- **Claude-path tuning score is in-sample too (side-agent note, 2026-10-20):** the proxy's prompt quotes three tuning messages with their answers (M0001, M0008, M0025), and its canonical food list is taken from the gold labels of all 170 tuning messages. So a Claude-path score on the tuning set is in-sample and must never be quoted as expected accuracy. It is reported twice: on all 170, and on the 167 without the three prompt examples. The 167 figure removes only the quoted answers, not the food-list overlap, so it is still in-sample.
- **Recorder pacing (Arjhine, 2026-10-20):** the Claude-path recorder sends no more than the proxy's limit: 30 requests per sliding 60-second window across all callers (`server/src/config.js` `RATE_LIMIT_PER_MINUTE`, `server/src/rateLimit.js`), so it spaces requests at least 2.1 s apart. On a 429, whether from the proxy's own limit or from Claude (the proxy returns `Retry-After: 60` for those), it waits `Retry-After` seconds and resends, up to 5 attempts per message and pass. Every attempt is a JSONL line with its HTTP status and attempt number. **Outages too (Arjhine, 2026-10-20):** the recorder also retries a 503 whose body error is `model_unavailable` (outages, timeouts, connection errors) and network errors, within the same 5 attempts, with backoff (2, 4, 8, 16 s). It never retries a 503 `model_output_rejected` or a 422: those are real parse outcomes. Every attempt's JSONL line carries its HTTP status and error field. The proxy adds an `error_kind` to `model_unavailable` (auth, bad_request, timeout, connection, server, other, no_client). The recorder stops the pass at once on `auth` or `bad_request`, or after 5 messages in a row with no usable response, because those are setup faults, not outages. The scorer uses the final response per message and pass that is neither a 429 nor a `model_unavailable` nor a network error. A message with none is unanswered: excluded from that pass's denominator, not scored wrong, and listed by id so any bias from outages is visible. Outage counts are reported per pass. **Every id, every pass (Arjhine, 2026-10-20):** the scorer loops over all 170 tuning message ids in every pass, not only the ids in the JSONL, and reports ids with no attempt line as "not sent", separately from unanswered. The recorder ends each pass file with a marker line (`pass_end`, status `completed` or `stopped`, with the reason). A pass without a `completed` marker, whether stopped or cut off with no marker, is left out of the means and the min–max spread and listed separately. With fewer than 3 completed passes, the report says so at the top and gives the spread over the completed passes only. **Same prompt only (Arjhine, 2026-10-20):** `GET /health` reports `prompt_sha256`, the sha256 of the exact system prompt built at startup, with the server's `git_commit` and `git_dirty`. The recorder copies these and the model id into every attempt line and the pass_end marker. It re-checks `/health` every 25 messages and stops the pass (`prompt_changed`) if the hash changes. **Whole request config (Arjhine, 2026-10-20):** `/health` also reports `request_config_sha256`, a sha256 over the system prompt, the JSON Schema from `zodOutputFormat(ModelOutput)` (keys sorted), the model id, effort, `max_tokens`, the installed SDK version, and the source text of `server/src/schema.js` and `server/src/parse.js` (normalised to LF line endings, so a Windows CRLF checkout gives the same hash). The recorder copies it into every attempt line and pass_end marker, and stops a pass (`request_config_changed`) if it changes. The scorer groups passes by this hash, not by the prompt hash alone: passes with different hashes never share a mean or min–max spread, each group is reported separately, and the report says so at the top. **Spend measured from logged usage (Arjhine, 2026-10-20):** every `/parse` response that came from a model call (200, 422, 503 `model_output_rejected`) carries the API's usage counts (input, output, cache-write and cache-read tokens). The recorder saves them in each attempt line, and the scorer reports total tokens and actual cost per pass from those logs, over every attempt including retries. Attempts with no usage (outages) are counted as cost unknown. The dry-run estimate leaves out thinking tokens and says so. One single paid call checks the real per-call cost before any 3-pass run, with Arjhine's approval. Each report gives the number of calls that got a 429 and the number of retries. For evaluation runs the proxy is started with its SDK retries off (`SALO_SDK_MAX_RETRIES=0`), so no attempt is hidden inside the proxy. A 429 is not billed; any other attempt may be.
- **Claude-path tuning score label (Arjhine, 2026-10-26):** the all-four mean 94.3% (93.5%–95.2%) over completed passes 1, 3 and 4 (`docs/reports/parser-claude-tuning.md`) is labelled **laptop proxy, tuning in-sample** wherever it is quoted. Model id, effort, `max_tokens` 2048, SDK 0.135.0 and the output JSON Schema (sha256 19b3f023422b…) are the same; the hash differs because the function hashes its own Deno `schema.ts`/`parse.ts` (as sha256 digests) where the laptop proxy hashes the source of `server/src/schema.js`/`parse.js`. So the 94.3% has not been measured on the Edge Function and applies to the laptop proxy only.

## M6 tuning and pilot (Arjhine, 2026-11-01; method details by the orchestrator, fixed before any tuning run)

- **Scoring formulas confirmed (Arjhine):** the proposed definitions above stand, including storage = 0.2 when the lot needs a fridge if kept and the pantry has none. Tuning chooses the weights, so it may make storage count less or not at all if that serves the target better.
- **Tuning target (guide p.12, the same for Salo and central greedy):** maximise mean food rescued (kg per evening) over E01–E10 subject to the mean, over E01–E10, of each evening's worst-served need met being at least 0.5. If no setting reaches 0.5, the setting whose mean is closest to 0.5 is used (ties: more food). Tuning evenings E01–E10 only.
- **Search (orchestrator; equal effort, guide p.11 and Wen et al.):** Salo tunes its four utility weights and the linear share-bid scale; central greedy tunes its four utility weights and its transport penalty per minute. Each gets the same budget of 400 evaluated settings from the same seeded sampler: weights drawn uniformly on the simplex (Dirichlet(1,1,1,1)), Salo's scale uniform on whole numbers 5–40, central greedy's penalty uniform on 0–0.02 per minute, plus the untuned starting setting as setting 0. Sampler seed 20261101. Each setting runs every tuning evening once with its fixed evening seed. The 40-share budget, D-Q1 and every engine rule stay fixed. Driver reliability starts from the dataset's frozen tuning estimates (no learning carried between evenings, guide p.15).
- **Freeze:** the chosen settings are written to a frozen-parameters file with a checksum before any pilot run, and the checksum goes into `src/results/registration.ts`.
- **Fairness check right after tuning (option A above):** if the tuned Salo's worst-served need met is still 0 on 6 or more of the 10 tuning evenings, stop; Arjhine picks a replacement measure before any pilot run.
- **Pilot approved (Arjhine):** if the fairness check passes, the pilot runs on E11–E20 with the frozen settings, including parser scoring on pilot messages (paid, inside the $5 budget below). Pilot numbers are never reported as results. **Main run approved (Arjhine, 2026-11-01, "I approve all"):** the main evenings and parser scoring on main messages may run, but only after the frozen-parameters checksum, the pilot and the main-evening count are written into `registration.ts`, in that order (guide p.19).
- **Smallest fairness gap worth caring about (Arjhine):** 0.10 of worst-served need met (the food gap stays 6 kg per evening, guide p.19). **Kept after review (orchestrator, Arjhine said proceed, 2026-11-01):** tuning later showed worst-served need met of only about 0.151 (Salo) and 0.166 (central greedy), so 0.10 is about two-thirds of that level, not the fifth assumed near 0.5. The gap was not changed, because the pilot had already run when this was raised, and a gap chosen after the pilot would be weaker than the one fixed before it. Limitation to report with the fairness result: a real difference smaller than 0.10 (for example 0.15 vs 0.20) is treated as not worth caring about, so the main run is not sized to detect it.
- **Main-evening count (amended by Arjhine, 2026-11-01, before any pilot run):** for each main measure (food rescued, worst-served need met), take the pilot's 10 per-evening differences d (Salo minus central greedy) and their sample SD s. Use the one-sided 80% upper confidence limit of the SD, s_U = s × √(9 / χ²₀.₂₀,₉) = s × √(9 / 5.3801) = 1.2934 × s (χ² lower 20% quantile, 9 degrees of freedom), instead of s itself. Then n = ceil((2 × 2.2414 × s_U / gap)²), with 2.2414 the two-sided 97.5% normal quantile and gap = 6 kg (food) or 0.10 (fairness). The count is the larger of the two n, and at least 10. **Why:** an SD estimated from only 10 pilot evenings is uncertain, and it is too small about half the time. Planning with the plain SD would then give too few main evenings, and the 97.5% intervals would come out wider than the gap. The upper limit covers the true SD with 80% confidence, so the count is too small only about 1 time in 5. (Side-note source; Papers With Code `pwc search` found nothing on it, since it covers ML papers. The practice is known from clinical-trial sample-size planning, but it was not cross-checked.) **Check after the main run (Arjhine):** report whether each 97.5% interval's full width is really below 6 kg (food) and 0.10 (fairness), either way.
