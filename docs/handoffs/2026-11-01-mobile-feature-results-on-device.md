# Handoff: Results on the device and the food-ceiling diagnostic, mobile-feature, 2026-11-01

## Summary

- **A. RES-01: the numbers are computed on the device.** The Results screen no longer shows a stored record. Every cell reads "Not measured yet" until the user taps **Run the main evenings** (shown only while the gate is open). The run executes the engine over E21 to E64 on the phone, one policy run at a time, yielding to the event loop before each run, with a progress line. The bootstrap runs in chunks of 250 resamples. Leaving the screen cancels the run. Results are kept in memory for the session only.
- **The stored record is out of the app bundle.** It is now a JSON test fixture, `docs/reports/m6-main/record.json`. No file under `src/app`, `src/components` or non-test `src/results` loads it (guard test). `src/results/mainResults.generated.ts` is deleted.
- **The on-device path reproduces the record byte for byte** (main, learning off, ceiling counts), on all 44 main evenings, in jest. The record regenerated by the gated run is byte-identical to the committed one.
- **B. Food ceiling, second definition (supporting only).** `ceiling hit = all posted food was rescued that evening (food rescued equals total posted kg within 0.001 kg)`. It is on the screen as the ceiling row, labelled supporting, and reported under both definitions for tuning, pilot and main in `docs/reports/m6-main.md` section 7.
- **Result of the ceiling counts: zero everywhere.** Under both definitions, every policy, in all three groups (tuning E01–E10, pilot E11–E20, main E21–E64), the ceiling is hit on 0 evenings. The second definition does not separate the policies on this dataset either (see Open risks).
- The main numbers did not change. No engine, parameter, measure or interval logic changed. No commit. No paid call. Nothing run on a device or emulator.

## Open risks

- **Device timing not measured.** The run is 352 engine calls. Jest takes 24 s on this machine, but a phone under Hermes could take far longer. Each engine call is synchronous and cannot be interrupted, so yielding happens between runs, not within one. The UI stays responsive between runs; a single run blocks for its full duration. Cancel takes effect after the current run.
- The progress bar animation (300 ms, instant under reduced motion) and the layout of the new rows have not been seen on a device.
- Results are kept in memory for the app process. Closing the app loses them, by design.
- **Stale E21 to E30 text left alone (outside the brief):** `docs/architecture.md` lines 197, 217, 562 and 567 still say E21 to E30. `docs/decisions.md` lines 184 and 198 (rules for parser and database) name E21–E30 as well. Only the requested stories and decisions bullets were changed.
- RES-07 in `docs/stories.md` still calls the ceiling definition an open question. It was not changed (not requested).
- The gated runs rewrote `docs/reports/m6-main.md` and the record. Their numbers are unchanged, as checked above.
